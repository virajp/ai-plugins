# DRY — Don't Repeat Yourself, and Its Limits

## Definition

Every piece of **knowledge** — a business rule, a constant, a schema, an
algorithmic decision — has one authoritative home; everything else derives
from or points to it. When the rule changes, one edit changes it everywhere.

The limit matters as much as the rule: DRY is about knowledge, **not text**.
Two code fragments that look identical but encode *different decisions* —
decisions that would change for different reasons — are not duplication, and
merging them couples things that must vary independently. The worst DRY
violations in practice are over-merges, not copies.

## Smells

Duplication smells:

- The same business rule, threshold, or mapping restated in two modules — and
  a bug fixed in one of them but not the other.
- A schema, enum, or error shape maintained by hand in two layers (the
  [engineering baseline](../engineering-baseline.md)'s contract rules exist
  precisely so schemas have one home).
- Parallel switch/branch ladders over the same discriminator scattered across
  files.
- Documentation restating what code or config already states, drifting.

Over-merge smells (the limits):

- A shared helper whose body is a growing ladder of flags and `if`s because
  its callers keep diverging.
- Two domains importing a "common" module for what was only coincidental
  resemblance, now unable to change without breaking each other.
- A base class existing only to hold code two unrelated things both happened
  to need.

## How a reviewer verifies it

- For an apparent copy, ask the **change question**: if this rule changed,
  would both sites *have to* change together? Yes → duplication, flag it.
  No — they could legitimately diverge → leave them apart, and flag any
  premature merge instead.
- Trace a changed constant or rule through the diff: did every restatement
  move? A restatement left behind is the finding.
- For a shared helper touched by the diff, count its behavior flags. Flags
  added so different callers get different behavior are an over-merge
  unwinding — recommend the split.
- Check derived artifacts (generated code, projections, caches) are actually
  derived — regenerated by the build — not hand-synced copies.

## Application patterns

- Give each piece of knowledge a **named home** and make the other sites
  consume it: derive, import, generate — never re-type.
- Apply the rule of three for incidental resemblance: tolerate a second copy,
  and by the third, merge — three call sites reveal what actually varies.
- Extract by **meaning, not shape**: name the shared thing after the decision
  it owns. If the only honest name is `util`, `helper`, or `common2`, the
  merge has no shared meaning and should not happen.
- Keep cross-boundary duplication mechanical: when two services must agree on
  a contract, share the contract artifact (a schema, per the
  [rest-api-design skill](../../skills/rest-api-design/SKILL.md)) rather than
  sharing implementation code across the boundary.

## When not to apply it

- **Test code** trades DRY for legibility: a test that restates its fixture
  plainly beats one that hides it behind shared setup a reader must chase.
  Repetition in tests is a cost, but coupling test cases together is worse.
- **Coincidental resemblance** — same shape today, different reasons to
  change — must stay unmerged. Independent evolution beats a shared
  dependency.
- **Across ownership boundaries** (separate teams, services, or release
  cadences), a little duplication is often cheaper than a shared library both
  sides must coordinate to change.
- When de-duplicating would breach a layer rule — e.g. business logic pulled
  into a technical helper to be "shared" — the baseline's
  business/technical separation wins over DRY.
